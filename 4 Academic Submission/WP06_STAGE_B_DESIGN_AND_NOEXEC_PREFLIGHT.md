## 2. Selected architecture and alternatives

**Recommended future profile:** separately launched, cooperative-only disposable non-Stata actors with a dedicated supervisor, local authenticated control/evidence channels and retained exact-process handles. No installed MCP/service integration, background service, system configuration change, Job Object assignment, kill-on-close, process-name search, shell command or automatic restart is part of this profile.

Alternatives considered: reusing the Stage-A thread harness cannot prove independent process behavior; modifying the installed Stata/MCP service violates this scope and introduces unrelated engine risk. A Job Object/forced-cleanup profile is deferred because containment and inherited/nested-job effects need their own adoption and exact termination authority. Windows documentation describes these mechanisms, not their safe deployment on this host. [Job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

The future ownership tree is `L → O → {S → W, C}`:

| Role | Responsibility and lifetime |
|---|---|
| L — launch attestor | Existing explicitly approved operator launcher; creates O, retains a query/synchronization handle and proves O's final exit. It is not a shared service or implicit Codex execution grant. |
| O — observer | Creates S and C, independently verifies signed observations, retains limited handles and accounts for all owned resources. It does not depend on C to observe S/W or act as S's deadline loop. |
| S — supervisor/registrar | Creates W, owns the single-writer journal and trusted registration, arms the watchdog before dispatch, and independently detects C exit/heartbeat loss. S is not a child of C. |
| C — controller | Issues only the predeclared synthetic work/cancel/fault messages. Its blockage or exit must not disable S. |
| W — disposable worker | Runs only a pinned non-Stata wait/queue fixture. Its cooperative control receiver is separate from its deliberately blocked work queue. No arbitrary code, data path, child spawn or model command is accepted. |

Maximum concurrent **new** actors per case: four (O,S,C,W). Default total launches: four. AC18 may predeclare two sequential controller generations; AC19 may predeclare two sequential worker generations; each has total cap five and never overlapping replacements. Those generations have new command/reservation/lease identities, are explicit fixture stimuli and are not retries of the consumed attempt. No unplanned extra launch or supervisor restart is permitted. All actual identities are absent today.

O shutdown is not self-proven: L must observe the same O process handle exit after O's final inventory. If L is unavailable, final cleanup remains unknown. If S dies, its potentially applied stop is never resent; O preserves uncertainty. W's proposed autonomous self-ceiling may assist bounded cleanup, but its own timeout is not evidence that S met its deadline. Missing cleanup or scheduling evidence fails/holds the case, rather than triggering unapproved termination.

## 3. Exact launch and identity boundary

Future process creation uses a pinned absolute executable and explicit application path, no PATH/shell/batch resolution, no raw free-form command, no inherited user environment, and only a minimal reviewed environment/working directory. Keys never travel in arguments, environment or logs. Allowed inherited/duplicated handles are enumerated per role; standard handles are valid explicit values, not incidental parent handles. Each failure preserves its inventory; successful process creation alone is not initialization/registration proof. [CreateProcess documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

The creator captures the returned process handle/PID, creation FILETIME, current generation, observer epoch, scope and exact approved build before the target can receive work. `GetProcessTimes` creation time is retained as its exact unsigned64-bit count, encoded as a canonical decimal string; exit time is not read as proof before actual process exit. A disk/script digest is provenance, not resident-bytecode attestation. Any required but unavailable provenance blocks arm. [Process timing](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes).

CreateProcess initially returns a broad process handle. The future bridge must duplicate down to explicit query/synchronization rights, close creator/primary-thread handles when safe, and record the handoff **before arm**. Observer handles never retain termination permission. Only the separately granted AC21 branch may retain one additional terminate-capable handle to its exact W target; broad rights are never treated as permission. No handle is closed while an associated wait is outstanding. [Process rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights), [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle).

The complete runtime binding is `origin, contract_digest, build_digest, host_id, boot_id, observer_epoch, session_id, owner_nonce, worker_epoch, command_id, pid, creation_time_100ns, engine_module_digest, reservation_id, lease_id, scope_id, clock_domain, qpc_frequency_hz`. Origin is B_DISPOSABLE; the module digest names the approved disposable interpreter/fixture, **never Stata**. IDs are bounded opaque ASCII strings; digests are64 lowercase hex; counts/times/PIDs are canonical decimal strings with explicit range checks. Actual runtime records are not included in this pending template.

Host binding means the same local kernel-object domain. Boot continuity uses a fresh approved observer epoch, same-machine QPC domain and retained live creator/target handles: every actor is created within that observer's uninterrupted lifetime, and no run can resume after observer loss/reboot. The logical `boot_id` is a conservative run-bound boot namespace, **not a claimed Windows boot GUID**; observer restart creates a new namespace even on the same boot. The future registrar must supply and verify that continuity evidence before arm. An old receipt or matching PID is insufficient. If a deployment needs a globally comparable OS boot ID, that is an additional unresolved provider/adoption gate, not an inferred fact here.

S alone owns the active registration and control application. Per-attempt handles/generation are immutable while work is active. AC19 retires the first generation, preserves its handles/evidence, then admits the predeclared second generation; a queued old message cannot inherit the new target. Control consumes the complete expected binding immediately at application, not just at queue admission.

## 4. Independent deadline path and journal ordering

S's watchdog is the sole cooperative-stop consumer. C/transport handlers can post a bounded cancel request but cannot directly apply control or acquire a lock needed by the watchdog. Work dispatch is prohibited until the reservation, one-stop authority slot, exact target/lease and deadline are committed and S emits SUPERVISOR_ARMED. An uncertain commit blocks dispatch; no retry or new IDs may bypass consumption.

At deadline or verified controller loss, the watchdog consumes that **precommitted single-use slot** once and signals only W's private cooperative event. It does not wait for C's response, pipe completion, journal append, work-queue lock or a thread on C's event loop. The single consumer freezes its applied/unknown disposition before processing another request. Post-action journal/receipt persistence can be late or unavailable; that means evidence/cleanup HOLD, not a second signal. This deliberate ordering prevents a blocked journal writer from becoming the cancellation path. It is a design obligation, not demonstrated behavior.

Kernel event signaling is a **control-delivery attempt**, not proof W observed/applied the stop. W must issue its independently scoped STOP_APPLIED observation when its receiver consumes the exact event/lease. O verifies that receipt, independently observes W's same-handle exit, then cleanup. A self-ceiling/natural exit without that receipt preserves exit but leaves cancellation cause unknown. No control action is credited from C's acknowledgment, a replacement worker, registry absence or an API request alone.

S is single writer to a new restricted local SQLite journal outside Git/synchronization folders. Cross-process readers use coherent read transactions; no writer retry. Recovery preserves the consumed ledger, quarantines old nonterminal leases and reconciles against a separately sealed high-watermark. Restoring a stale backup cannot reopen work. Stage-A code and synthetic keys are not used as an operational store/backend; a new reviewed B build is required.

## 5. Transport, authentication and completion

Future transport uses explicit restricted local Windows named pipes with remote clients rejected, bounded overlapped I/O and separate control/evidence versus deliberately blocked work/response channels. The S watchdog-to-W private event is not dependent on a pipe response. Pipes have an explicit role/target-specific ACL, peer PID-to-retained-handle/creation/generation checks at registration and consumption, maximum frame8192bytes and bounded pending operations; same-SID principals are not assumed independent adversaries. Default pipe permissions are not accepted. [Pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [pipe creation flags](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea), [client](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid)/[server PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid).

Fresh per-case/per-role nonproduction credentials are provisioned only through approved private bootstrap handles/storage, never Stage-A's public ART keys. Canonical ASCII messages cover the entire binding, issuer/credential/scope, sequence, previous body digest, QPC tick/frequency/domain, kind/reason/result and fixed payload digest. Role-kind allowlists separate C requests, S registration/control attempts, W applied observations, O verification/cleanup and L final-observer exit. Keys require an adopted lifecycle/access/revocation/recovery policy; shared-key holders can forge and are not an independent nonrepudiation authority. No key or ACL is created now.

One OVERLAPPED/event and retained buffer belongs to each outstanding operation; lifetime extends through observed completion. CancelIoEx requests cancellation but does not itself establish completion; late success, cancellation and failure outcomes are distinguished. Unknown completion retains/quarantines resources and blocks adoption. There is no infinite wait, busy-spin, response-dependent shutdown extension, freed pending buffer or close-during-wait shortcut. [Overlapped I/O](https://learn.microsoft.com/en-us/windows/win32/ipc/synchronous-and-overlapped-input-and-output), [CancelIoEx](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex).

## 6. Clock, budgets and success criteria

Proposed B profile uses raw Windows QPC ticks plus frequency, mapped to the adopted monotonic domain; it is the validated-Windows-counter alternative to the earlier generic monotonic_ns recommendation, **not an adopted change today**. O/S/W must establish same local domain/frequency/observer epoch. UTC is audit only. Convert an approved nanosecond allowance by integer floor `ticks = ns * frequency // 1_000_000_000`, rejecting zero, overflow or unknown values. No floating-point arithmetic. Deadlines are absolute; equality expires. Cleanup is the earlier of approved total ceiling and stop tick plus approved allowance; retries, implicit grace and deadline extension remain zero.

The exact runtime fields are null in gates.json: execution, cleanup, IPC, heartbeat interval/loss, autonomous worker ceiling, actor shutdown, scheduling-delay bounds and QPC frequency. No real budgets are selected, copied from ART100/110/113, measured or defaulted here. The operator must authorize a bounded calibration/provisioning scope before any measurement/target launch; launch and control acceptance require their separately sealed numeric ceilings and evidence. Such authorization is not supplied by this design.

QPC supports same-machine interval comparisons but does not establish real-time scheduling or synchronization to UTC. Cross-thread/process observations within one tick have ambiguous ordering; external timing claims require the conservative upper observation bound to be strictly before the deadline, otherwise TIMING_ORDER_AMBIGUOUS/late evidence cannot pass. S's local same-thread deadline comparison remains exact in its domain. A relative OS wait alone is not the deadline: recompute remaining QPC budget after each completion/wake; sleep/resume, unknown delay, domain discontinuity or inability to establish ordering quarantines the case. [Microsoft timing guidance](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps), [wait semantics](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

Separate dimensions are mandatory: lease/reservation, control attempt, W application, original-process exit, cleanup, evidence integrity and scientific validity. Runtime case outcomes are PASS_WITH_VERIFIED_EVIDENCE, FAIL_PRESERVED or BLOCKED_MISSING_PREREQUISITE in a **new** result packet only. Current cases remain NOT_EXECUTED. No arbitrary caller Boolean, nonempty path, signature field or metadata-checker PASS can confer runtime acceptance.
