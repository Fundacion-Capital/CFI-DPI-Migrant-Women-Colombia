# WP06 — read-only native loader diagnosis and bounded proposal

**Disposition:** the saved failure is localized to native Python/SFI discovery at the PyStata initialization boundary. Its internal cause is **not proven**. No loader change or trial is authorized or implemented here. The V4 failed trial and V5 offline qualification remain distinct and unchanged.

## What the exact evidence establishes

1. The scoped V4 worker record captured integer **−7100**, before the pinned PyStata code continued to system configuration. Installed `config.py:180–208` forwards the existing raw executable string through `-pyexec`; lines 253–267 mark SFI unavailable on −7100 and continue. The worker log records the shared-library discovery warning and the later `import sfi` failure at line 544. Adding the SFI module's directory would not prove that Stata loaded Python or registered the native plugin.
2. The raw handoff and the saved `prefix` and `base_prefix` use the uv minor-version path spelling. The current path is a junction to the exact pinned patch-version installation. Its executable resolves to the pinned file and hashes identically. The installed executable, `python311.dll`, and Stata engine are PE32+ x64; all three, vendor `config.py`, and Python `Lib/sysconfig.py` match the historical strict inventory. That rules out the simple explanations that this pinned DLL is absent on disk now or that these three pinned images disagree on architecture. It does not prove which DLL was sought, whether it mapped, or whether its transitive dependencies were available to native discovery.
3. The pinned engine contains static probe-like strings for Python prefix, base executable prefix and `sysconfig.get_config_vars('LIBDIR')`. The pinned Windows Python source initializes keys including `BINDIR` and `LIBDEST`, but does not define `LIBDIR`. If the exact embedded `LIBDIR` expression ran with that unmodified configuration dictionary, concatenation with the missing value would be a plausible failure path. The saved packet does not show that the Windows branch executed that expression, what interpreter/environment a subprocess used, what it returned, or whether a fallback was taken. This is a discriminator to investigate, not a reason to patch `sysconfig`.
4. A prior isolated trial already added the pinned process-local DLL directory and still reached the same SFI failure family. Python's documented API affects dependency search for extension modules and ctypes; it is not evidence that Stata's independent discovery logic or any discovery child used that directory. The generic PyStata setup documentation explains importing PyStata, but does not validate this isolated uv configuration or private `-pyexec` handoff.

References: [Stata 19 PyStata configuration](https://www.stata.com/python/pystata19/install.html), [uv minor-version directories](https://docs.astral.sh/uv/concepts/python-versions/#minor-version-directories), and [CPython 3.11 DLL-directory API](https://docs.python.org/3.11/library/os.html#os.add_dll_directory). Host-specific claims rest on pinned local files and saved receipts, not generic documentation.

## Minimal candidate: canonicalize only the pinned executable handoff

The smallest evidence-backed **candidate**, not a verified repair, is an additive disabled V5-based variant that supplies the already-pinned canonical executable to the vendor resolver boundary instead of the observed minor-version junction spelling. Reuse the existing temporary source-pinned resolver instrumentation. At the exact observed raw spelling, require that both strings resolve to the same pinned executable bytes, then forward the canonical string as the one changed `-pyexec` argument. Fail closed on foreign, missing, changed, or otherwise unexpected resolution. Restore the original resolver and retain the existing original-return/exception behavior. Preserve separately the vendor's original string and the actual string forwarded, using a new versioned receipt and strict reader rather than changing the meaning of the historical fields.

This is a one-variable test of the **path spelling handed to discovery**. It does not change worker or SDK interpreter launch, Python distribution, `sys.executable`, prefixes, environment, DLL directory, cache policy, vendor files, settings, deadlines, rollback rules, or SFI success criteria. It does not test every way aliasing could affect process startup. The source-exact artificial fixture used a fake native function and confirmed that only argument index 3 changes; it says nothing about the real loader response. Before any proposal to execute: require artificial rejection of foreign inputs, resolver restoration, exact actual-handoff and result readback, and unchanged disabled admission and containment.

**Decision rule:** Do not repeat the same trial unchanged. Do not activate this candidate now. If later separately adopted and authorized, a source-exact empty-only comparison would require actual handoff evidence, native return, positive SFI/plugin and loaded identity proofs, and complete terminal evidence. If it still returns −7100, stop rather than stack another path tweak. To choose a further loader change, first obtain evidence that identifies the Windows discovery branch and its failed lookup (for example, supported vendor diagnostics or a separately authorized bounded trace). Do not infer a PATH, registry, missing-LIBDIR, alias, or Java fix from the current saved trace.

The audit rechecked 33 inherited seals, four later seals, the 57-member V5 seal, all 21 consumed-run files, and five pinned runtime artifacts. The work used static file checks and an artificial argument fixture only.
